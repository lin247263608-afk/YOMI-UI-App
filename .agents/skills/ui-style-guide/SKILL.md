# UI 风格稿网页生成

把「线框稿/需求」转成一个可评审的多风格视觉稿网页：左侧（桌面）或顶部（移动）切换风格，右侧展示该风格的设计灵感、描述、主色卡，以及 3–5 张页面稿。

## 第零步：判断模式（决定发挥边界）

先看用户手里有什么，三种模式后续流程不同：

- **模式 A-1 · 有原型，只换皮肤**：用户提供了线框稿截图 / Figma / 明确字段清单，且只要求风格变化。→ 内容严格照搬，不新增任何功能点；布局也尽量保持原样。
- **模式 A-2 · 有原型，允许 UI/UX 优化**：用户提供了原型，但同意我从 UI/UX 角度对布局、信息组合、视觉层次做优化（例如：把散落按钮合并成卡片、把两步入口折叠成一步、调整标题位置、合并同类字段）。**内容必须严格克制**：不新增功能、字段、文案；只改呈现方式。动工前必须问一句：“在原型字段不变的前提下，是否允许我适当调整布局与信息组合来优化视觉/体验？”
- **模式 B · 只有功能或需求**：用户只说「做一个 XX 的下单页 / 一个骑行社区首页」。→ 我负责发散，把需求补成完整的信息架构：定义页面清单、每页模块、字段与示例数据、状态文案、空态/异常态，主动给出我认为该有的功能点。

模式 B 里「不许发挥」是错的；模式 A-1 里「发挥」是错的；模式 A-2 里只准优化布局、不准增删内容。开工前先在一句话里说明当前按哪个模式走。


## 第一步：对话确认核心内容（必须先问，不要直接开写）

用 ask_questions（可分两轮）收敛以下 6 项。用户已在需求里说明的不要重复问。

1. **项目与场景**：产品名/品牌名、业务场景（例：跨境电商、本地生活、SaaS 控制台、内容社区）、目标用户群。
2. **要出稿的页面**：页面清单 + 原型编号（例 `P-001 首页`、`P-002 详情页`）。建议 3–5 个核心页，覆盖多端时按端分组。模式 B 下由我提议页面清单，让用户增删。
3. **内容来源**：线框稿截图 / Figma 链接 / 文字字段清单 —— 有则进模式 A；用户明确说「你来定」或拿不出稿子，就进模式 B，不要反复索要原型。
4. **风格方向数量与倾向**：几套方向（建议 3–6 套）。从下方「风格库」里挑，或用户自定。方向名统一用英文短名（Minimal、Neo-Brutalism、Editorial…）。不要把上一个项目用过的那几套当成默认清单端上来。
5. **色彩**：主色/辅色，或提供 logo 让我取色。
6. **图片占位**：banner / 头图 / 路线图 / 空态插画是否需要真实图片；如需，确认业务类型与地域（用于选图方向，见「图片占位」一节）。

确认后用一句话回述结论再动手。


## 风格库（每次现挑，不要复用旧项目的固定几套）

先按项目气质与目标用户，从下面这些 UI 界主流方向里挑 3–6 套，并保证跨风格差异明显（圆角、描边、分隔方式、字重跨度、卡片处理、图片用量、主色面积至少 3 项互斥）：

- **Minimal / Swiss**：大留白、细线分隔、无阴影，主色只用于状态与金额。
- **Editorial / Magazine**：衬线大标题、栏宽对比、图文混排，内容型产品友好。
- **Business / Corporate**：深色头部＋白色浮起面板，等宽数字，沉稳专业。
- **Neumorphism-lite / Soft UI**：同色系底与柔和双向阴影，克制使用避免可读性问题。
- **Glassmorphism**：半透明层＋背景模糊，需要有底图才成立。
- **Neo-Brutalism**：粗描边、硬阴影、高饱和色块、超粗字重，年轻/社群化产品。
- **Material 3 Expressive**：动态取色、大圆角容器、分层高度，安卓生态友好。
- **iOS / HIG Native**：系统级分组列表、分段控件、毛玻璃导航，原生感强。
- **Bento Grid**：模块化方格拼贴，适合数据密集首页与仪表盘。
- **Dark Mode First**：深色底＋霓虹强调色，工具类/夜间高频场景。
- **Ticket / Boarding Pass**：直角边框、虚线撕线、等宽编号，票务与行程契约感。
- **Ins / Lifestyle**：暖白底、大圆角、柔和投影、大幅实拍图，传播型内容。
- **Playful / Vivid**：高饱和、插画或大 Emoji、圆润几何，活力型社群。
- **Data-dense / Console**：小字号高密度、表格化、状态色系统，B 端后台。

每套都要写出「适用与代价」一句（例：Neo-Brutalism 拉年轻用户好感，但商务客户会觉得轻），写进 `description` 结尾。


## 图片占位（要真实图，不要灰块）

- 只要页面有 banner / 头图 / 路线图 / 空态插画位，就放真实图片，不要灰色占位块。
- 选图方向按项目推断：业务类型（出行 / 餐饮 / 教育 / 医疗 / 电商 / 金融…）＋ 地域（英国 / 日本 / 国内 / 东南亚…）＋ 场景（机场航站楼、街景、车内视角、办公桌、城市天际线）。推断不出来时用中性的「场景照 + 低饱和」而不是抽象渐变。
- 统一处理：低饱和、弱对比、不抢文字；深色文字压图时加 ink 渐变遮罩；固定裁切比例（首屏 16:9 或 3:2，卡片缩略 1:1）。
- 来源优先级：项目内 `src/assets/` 已有图 → 用 generate_image 生成写实照片风格图存到 `src/assets/`（ES6 import 引入）。禁止外链热链图片。
- 同一页面在不同风格里可以用不同处理（铺满 / 圆角卡内 / 不用图），但图片主题保持一致，方便横向对比。


## 铁律：内容 vs 样式

- **模式 A-1**：内容、字段、参数、状态文案、布局严格来自线框稿/用户提供，禁止自行新增功能（定位、ETA、实时进度、奖励、评分、里程、聊天入口等一律不加）；拿不准的字段先问，不要补。
- **模式 A-2**：字段与功能内容严格锁定，但布局与信息组合可优化。允许做：卡片化、折叠同类项、调整标题与入口层级、合并步骤、提升视觉动线；不允许做：新增字段/按钮/状态/功能文案、修改字段名称或含义。每处调整都要能对应回原型的已有内容，不凭空造。
- **模式 B**：内容由我设计，但要先输出一份「页面 → 模块 → 字段/示例值」清单（可直接写在回复里）给用户确认，再落成组件；确认后这份清单就变成模式 A-1 的基线，之后不再随风格增删内容。
- **样式、排版、色彩、层次 = 三种模式都自由发挥**，每套方向必须有一眼可辨的差异（底色、圆角、描边、字重、分隔方式、图片使用）。
- 风格描述里**不要提**「基于原型/Figma/线框稿」，要像真实设计说明。


## 页面结构（固定）

```
src/routes/index.tsx                     风格稿容器（sidebar + 内容区）
src/components/style-guide/Phone.tsx     手机/页面外框 + 可选 TabBar（如项目需要）
src/components/style-guide/v1/*.tsx      方向 1 的各页面
src/components/style-guide/v2/*.tsx      方向 2 …（每套一个目录）
```

容器内维护一个 `styles` 数组，每项：

```ts
type Style = {
  id: string; name: string;            // 英文方向名
  summary: string;                     // 侧栏一行概述
  inspiration: string;                 // 设计灵感（2 句）
  description: string;                 // 风格说明（3–4 句，含适用场景）
  palette: { name: string; cls: string; hex: string }[];  // 3–4 个主色
  screens: { code: string; label: string; node: ReactNode; dark?: boolean; fluid?: boolean }[];
};
```

布局要求：
- 桌面：左侧 `lg:w-[292px]` 固定风格列表（选中态用 ink 底），右侧顶部介绍 + 色卡，下方页面稿横向排列。
- 移动：`sticky top-0` 顶部横向滚动 tab，介绍与页面稿竖排。
- 页面稿一律用 `Phone`（或等比例外框），页面过长传 `fluid` 拉伸外框高度而非裁切/出滚动条；深色头部页面传 `dark` 让状态栏反色。
- 参考实现：`references/Phone.tsx`、`references/style-guide-page.tsx`。


## 设计系统

所有颜色写进 `src/styles.css` 的 `:root` + `@theme inline`（oklch），组件里只用语义 token（`bg-brand`、`text-ink`、`bg-go`…）。禁止 `text-white` / `bg-[#xxx]` 硬编码。常用扩展 token：`brand`、`brand-soft`、`brand-foreground`、`ink`、`ink-soft`、`go`、`surface`、`surface-alt`、`shadow-card`。


## 收尾

- 每个方向的同一页面内容必须一致，只有样式不同（方便横向对比）。模式 A-2 下优化后的布局结构也必须跨风格保持一致。
- 路由 `head()` 写项目专属 title/description/og。
- 交付时一句话说明有哪些方向，并邀请用户逐个方向提修改意见（模式 A-1 常见反馈：内容过度发挥、某块占比过高、缺品牌/语言切换；模式 A-2 常见反馈：某处优化改变了原本操作流程；模式 B 常见反馈：某个模块不需要、字段命名要改）。
